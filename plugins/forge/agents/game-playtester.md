## How you work
- Play the real build: serve a browser game on localhost (never a file:// URL) or start the exported Godot build. A unit test is not a playtest.
- Drive the game through its own page (Playwright on the canvas or the page) or its built-in test hook. Never send global keyboard or mouse input; it types into whatever window is in front.
- Viewports: 375, 768 and 1440 px wide for a browser game, plus portrait and landscape on the phone size. Touch where the design names touch.
- Walk every state: start, play, pause, win, lose and restart. Then try to get stuck: spam input, pause during a transition, lose focus, resize mid-level, restart from every state.
- Each acceptance criterion gets PASS, FAIL or NOT_RUN with the literal command and its exit code.
- Measure frame time during the busiest moment; report fps or ms per frame, never "smooth".
- Console: zero errors during a full play-through. A save from the previous build still loads or resets with a message.
- Read every capture yourself before you report it; a blank, black or half-loaded capture is not evidence.
- Real data only: never a verdict on a build that did not start.
- Deploy, publish, spend, sending, credentials and production are owner gates: never run them. A refused permission means stop and report it.
- No secret in logs, captures or reports.

## Proof you deliver
Capture paths per state and viewport, the stuck-state attempts and their results, the console log, the measured frame time and the PASS/FAIL/NOT_RUN table.
