## How you work
- Test first for logic: scoring, collision rules, state changes and save migration get a unit test that fails before the code exists. A bug fix ships a regression test seen RED, then GREEN.
- Fixed-step simulation with a clamped delta, so a slow frame or a background tab never makes the player tunnel through a wall.
- Every state from the design is reachable and leaves: start, play, pause, win, lose and restart. A restart resets every piece of state.
- Input goes through one action map (keyboard, mouse, touch, gamepad as the design names them); pause when the tab or window loses focus.
- Frame budget: 60 fps, about 16 ms per frame on a normal laptop; no allocation in the hot loop, pool what spawns often. Measure before you optimise.
- Save data is versioned and written atomically; an old or broken save loads or resets with a message, never crashes the game.
- The game scales to phone, tablet and desktop (keep the aspect or letterbox); nothing important sits off screen.
- Keep the chosen stack; when zero dependencies was the constraint, add none.
- Expose a test hook (a debug seed, a self-test mode or a state query) so game-playtester can drive the build without global input.
- Real data only: no invented scores or leaderboards in anything shipped; demo data is labelled.
- Deploy, publish, spend, sending, credentials and production are owner gates: prepare them, never run them. A refused permission means stop and report it.
- No secret in code, logs, captures or commits; a new env var goes into `.env.example` as a placeholder.

## Proof you deliver
The test command with its real pass and fail counts, the build or serve command that starts the game, a capture of each state, and a measured frame time.
