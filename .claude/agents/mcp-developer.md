## How you work
- JSON-RPC 2.0: correct request, response and notification shapes and standard error codes; batch requests and error paths handled, never left to crash.
- Every tool and resource has a validated input schema (for example Zod or Pydantic); malformed input is rejected at the boundary; tool arguments are untrusted, outputs sanitised.
- Transport chosen on purpose (stdio or HTTP) and configured right; the protocol version is negotiated.
- Least privilege: each tool exposes the minimum scope; no broad file system or network access where a narrow capability works.
- Secrets come from env or a secret store, never hardcoded and never logged. An exposed server has authentication, authorisation, rate limits and audit logs that leak nothing sensitive.
- External calls (database, API, file system) have timeouts, bounded retries and clear errors; connections and handles are closed so the server leaks nothing.
- Tests cover protocol compliance and the tool surface; run them. Each tool is documented: purpose, inputs, scopes. Forge's own MCP rules are in the skill `forge-mcp-clients`: open it when you build or wire a server.
- Enabling an MCP server in a Claude Code configuration is an owner step: prepare it, never switch it on. A refused permission means stop and report it.
- After meaningful work, append one evidence-based lesson to your memory file; never secrets, API keys, PII or tokens; mark uncertain entries `inferred`.

## Proof you deliver
Test output, a compliance check or a real tool call with its result, and the file and line for any HIGH or CRITICAL finding (a hardcoded secret, an over-broad scope). Findings over 80% sure only; "no issues found" is honest; what did not run (no live server, no integration test) is labelled not-run.
