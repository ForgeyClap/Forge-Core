# forge-electron — Release: signing, auto-update, the unsigned path

Provenance: Forge-native. Pattern adapted from pedronauck/skills `skills/curated/electron-release` (licence not
confirmed, so ideas only, no text; its broad Bash grant and its unattended tag-and-push step were deliberately
left out) and from the Tauri signing/updater material in hairyf/skills `skills/tauri` (MIT, see `../LICENSE`).

## Owner gates (always)
- Tagging, pushing, publishing a release, uploading to a store or update server, and buying a certificate are
  **owner actions**. Agents prepare the config and a local build; the owner pulls the trigger.
- Signing keys, `.p12`/`.pfx` files, Apple IDs, app-specific passwords and API keys live in the CI secret store or
  the OS keychain. They are never printed, committed, pasted into chat or written to logs, and agents do not read them.

## Signing matrix
| OS | What | Notes |
|---|---|---|
| Windows | Authenticode code-signing cert (OV, EV, or a cloud signing service such as Azure Trusted Signing) | Unsigned = SmartScreen "unknown publisher"; EV builds reputation faster. A TLS cert is not a code-signing cert. |
| macOS | Developer ID Application cert + **notarization** (outside the App Store) | Needs a paid Apple account; hardened runtime and entitlements must match what the app does. |
| Linux | Optional GPG signing per package format (deb/rpm/AppImage) | The distribution channel decides. |

Order matters: build → flip fuses → sign → notarize (macOS) → package the installer → sign the installer.

## Auto-update (electron-updater / update.electronjs.org)
- Use `electron-updater` (with electron-builder) or Electron's own update service; never a hand-rolled downloader.
- Updates are only safe on **signed** builds: the updater verifies the signature/hash of what it downloads.
  Never ship an unsigned silent updater.
- HTTPS only; the update feed (`latest.yml` and friends) is generated by the build, never hand-edited.
- Staged rollout: release to a percentage first, watch crash and launch reports, then widen. A bad release is
  rolled back by publishing the old code under a higher version.
- Test the update path locally (old version installed → new version served) before calling it done.
- Tauri: the updater has its own signing key pair (see `tauri.md`).

## The honest unsigned path
When there is no certificate (common for a first build or an internal tool):
- Ship it labelled **unsigned**: say so in the report and the README, including what the user will see
  (SmartScreen "More info → Run anyway"; macOS Gatekeeper right-click → Open).
- **Disable silent auto-update** in an unsigned build; at most show a "new version available" link.
- Record "code signing: not-run (no certificate)" in ship-readiness; never claim a signed build.

## Pre-release checklist
- Version bumped in one place; changelog written.
- Fuses flipped, CSP strict, no devtools/inspect flags in production, no test/demo data in the bundle.
- Dependency review done; native modules rebuilt for the shipped Electron version.
- Installer built for each target and **installed + launched on a clean machine or VM** (screenshot/log as evidence).
- Signature verified (`signtool verify /pa` on Windows; `codesign --verify` and `spctl -a` on macOS) — or labelled unsigned.
- Update path tested from the previous version — or auto-update explicitly out of scope.
