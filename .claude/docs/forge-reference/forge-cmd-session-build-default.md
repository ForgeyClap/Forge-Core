## Forge Session Mode (project-local)
`/forge`, `gebruik Forge`, `gebruik Forge systeem`, `use Forge`, `start Forge` (or `start Forge session`) → enter **Forge Session Mode** for THIS project: set `.claude/FORGE_SESSION_STATE.json` `mode:"on"` (+ `since`). While ON, treat **follow-up prompts in this project as part of the current Forge session** — automatically run them through the Forge flow (Lead Agent + dynamic subagents); the user need not repeat "gebruik Forge"; keep dashboard/memory/task-history/ledger updating. **Pause/stop:** `stop Forge`, `pause Forge`, `normale Claude mode`, `doe dit zonder Forge` → set `mode:"paused"`/`"off"`. **Status:** `Forge status` / `is Forge actief?` → read + report `FORGE_SESSION_STATE.json`. Session Mode grants **no extra permission**: project isolation stays ON, ECC Normal ON, ECC Full Test OFF (unless explicitly enabled), and no credentials/live-workflows/production deploy/global config/external writes without explicit approval. The dashboard shows a **FORGE SESSION** badge from this file.

**BUILD BY DEFAULT (beginner-first — external audit 2026-09-23 replaced the old ARM → START gate; config-driven since v2.7.0, 2026-09-24).** Do the setup first, but never stop for it. Each step below follows an owner setting — read it with `node .claude/forge-bin/forge-config.cjs get <key>`; everything is ON by default and `/forge config` changes it. In order: **target folder** — the current working directory; state it in the first line and never ask which folder when the cwd is a project (writing outside the root is already a hard gate); if the cwd is the user's home folder or a drive root, refuse in one plain line ("Forge werkt alleen in een projectmap — maak een map en open Claude daar") and stop → **goal intake** (config `intake`: `silent` = answer the intake questions yourself from the mission text, the project scan, `.claude/.forge-setup.json` — written by `/setup-forge`, never re-ask what it already holds — and `FORGE_PROJECT_PROFILE.md`, recorded in the PRD under *Assumptions (auto-filled)*; `interview` = the `/forge interview` flow). With config `prompt-doctor` on, first run `node .claude/forge-bin/forge-promptcheck.cjs ask "<raw request>"` on the raw request: exit 3 → ask exactly its `nextQuestion` (options A/B/C + "iets anders", A recommended) as the ONE allowed question; otherwise record its `assumptions` under *Assumptions (auto-filled)*. Ask the owner at most ONE question, chosen by the `forge-prompt-coach` skill (only when two readings lead to materially different builds, or for an outward/irreversible action), as 2–3 plain-language options + iets anders, then confirm in one sentence (Ik bouw dus: … Klopt dat?) → **dashboard** (config `dashboard` on): `GET http://127.0.0.1:4100/api/health`; if it fails and `command-center/gateway/supervisor.mjs` exists in this project, start it yourself in the background and re-check for 5 s; if it does not exist, post one line `Dashboard not installed here (optional) — continuing without it` — **never print a start or build command for the user to type** → **usage guard** (config `usage-guard` on): run `node .claude/forge-bin/usage-guard.cjs start` yourself; the tool prints its own disclosure only when a new watcher really starts (repeat those lines once), says "already running" otherwise, and exits 3 without starting anything when the owner switched it off → run_id (`run.json` status `"running"`) → **git checkpoint** (config `git-checkpoint` on, an L2+ build or any destructive request, and `git status --porcelain` not empty), in this order — validate BEFORE staging, never stage-then-unstage (SECRET-CHECKPOINT): (1) `node .claude/forge-bin/forge-setup.cjs gitignore` — append-only, it makes `.gitignore` keep every secret-shaped name out of git BEFORE anything is staged, and reinforces any pattern a pre-existing `!negation` was defeating; (2) `node .claude/forge-bin/forge-setup.cjs checkpoint-scan --json` — validates every candidate path `git add -A` is about to pick up against the SAME shared credential-name policy `protectSecrets()` exports (`CHECKPOINT_SECRET_LINES` + the `.env*` guard lines: `.env*` except `.env.example`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`, `credentials*.json`, anything under `secrets/`) — exit 3 (and the printed JSON's `ok:false`) means either one or more secret-shaped candidates are not confirmed git-ignored, OR the candidate scan itself failed (git error/unreadable output) and therefore cannot vouch for a clean tree (V11/V12: read the JSON `ok` field yourself, never trust the exit code alone, both must agree); the checkpoint REFUSES right there, names the file(s) or the scan failure and why, and stages nothing — **a refused checkpoint never stops the build**: say once, in one plain line, that no safety checkpoint was made this run and why (the exact file name(s) or scan failure), then continue straight into building without one; never hand the beginner a command to run themselves (no `git rm --cached …`, no manual `.gitignore` edit — that remains Forge's own job, done by the tool, not printed as a step for the user); (3) only once BOTH the exit code is 0 AND the JSON says `ok:true`, `git add -A`; (4) `git commit -m "forge: checkpoint before <run_id>"` on the current branch (or on a `forge/checkpoint-<run_id>` branch when the owner's branch must stay clean) — local only, NEVER pushed; log it as `command_run`; not a git repo → say so in one line and skip → CLAUDE.md + Mission Blueprint + **PRD for any L2+ build** (`node .claude/forge-bin/forge-prd.cjs write '<prd-json>' --run <run_id> --tickets` — one ticket per acceptance criterion; L1 one-file fixes and pure research/review runs skip it and say so) + work packages → **contract preview** (`node .claude/forge-bin/forge-runcontract.cjs check --run <run_id>` — expect NOT DONE now; you now KNOW the rules this run must satisfy) → subagent roster (never more than config `team-max` Bosses at once; with config `model-tiering` on, pick each subagent's model per MODEL ROUTING below). **Destructive words** in the request ("opruimen", "verwijder", "clean up", "delete", "remove", "wipe") → the plan lists exactly what will be deleted — the keep-list first — and the git checkpoint above is mandatory before it; never "clean up" a folder wholesale. Then post exactly one line — `Plan ready — <n> work packages · team: <bosses> · Building now — say STOP to pause.` — and **continue straight into building**. **START gate = config `start-gate`:** `off` (default) = never wait for START; `l4-only` = wait for an explicit START only on an **L4** (phased) mission; `always` = wait on every build. "wait", "ask first" or "plan only" from the owner always win for that run, and STOP always works. With config `explain-mode` on, give each phase ONE plain-language sentence ("Wat ik nu doe en waarom: …") — never more. **"Smallest team" is about team SIZE, and the ceremony scales with the level:** an L1 one-file fix may run as ONE Boss with ONE verify pass; L2+ always gets plan + subagents + verify. Bare folder (no `.claude/forge-bin/`)? Copy `~/.claude/forge/template/.claude` into `./.claude` NOW (touches only `.claude/`), then run `node .claude/forge-bin/forge-setup.cjs gitignore` so secret-shaped files are kept out of git from the start, say in one line what was installed, and continue — never merely offer; if that template is absent, say so in one plain line (Forge itself is not installed on this machine; its installers are `install.sh` / `install.ps1`). **NEVER author/redesign your own dashboard — always COPY the canonical one** (a different self-made dashboard is a FAILURE). The hard gates — deploy, push, spend, DNS, production, credentials, activating a live workflow, sending anything out, killing processes by name, destructive deletes, git commands that throw away uncommitted work, writing outside the project — are unchanged and always interrupt.

**BEGINNER PROMISE (owner directive 2026-09-24).** Forge does it for you. It runs every command, script, install and build itself and never asks the user to run a file or code — no "run this in your terminal", no "open PowerShell and type …"; when a step truly needs the person (logging in, a paid key, an approval), it names exactly that one thing in plain words. It never asks "shall I continue?" / "moet ik verder?" between phases (autonomy `continue-within-mission`, `start-gate off`, standing rule `does-it-for-you`). It stops for the hard gates — deploy, push, spend, DNS, production, credentials, activating a live workflow, sending anything out, killing processes by name, destructive deletes, git commands that throw away uncommitted work, commands that hide what they run, printing a secret file's contents (`.env`, keys), writing outside the project — and for a real usage-limit pause (`node .claude/forge-bin/forge-autonomy.cjs decide "<phase>" --phase --live`). Say precisely what "stops" means when you repeat this to a user: five of those gates (destructive deletes, kill-by-name, git commands that discard work, opaque execution, printing a secret file's contents) are enforced by the PreToolUse gate hook that blocks the shell command before it runs — a classifier, not a proof: what it does not recognise it does not stop; the other gates are rules YOU follow, checked by a text classifier (`forge-actiongate`), not a technical stop — so never promise "always". Everything is ON by default, and `/forge config` lists every setting with its value and changes any of them in one command. When a command fails, explain it in plain words first (`node .claude/forge-bin/forge-explain-error.cjs "<error text>"` gives one sentence plus the safe next step) and then take that step yourself instead of handing the error to the user.
