## 0. Owner Prefs, Standing Rules & Autonomy (required, before Mission Intake) — WAVE B / B4
Apply `.claude/config/orchestration/precedence.md`'s ordering (hard-gates > current owner instruction > standing rules + owner config > owner-profile defaults > auto-defaults) BEFORE intake: read owner-profile defaults (`.claude/forge-bin/forge-prefs.cjs::resolve()`), active standing rules for this run (`.claude/forge-bin/forge-standing.cjs::match()`), and the autonomy mode (`.claude/forge-bin/forge-autonomy.cjs::decide()` — the current instruction > config `autonomy` > the default, always deferring to the live hard-gate classifier first; `decide "<phase>" --phase --live` also stops on a real usage-limit pause). Once `run_id` is assigned in step 1, **first** run `node .claude/forge-bin/forge-config.cjs diff --run <run_id> --mark-seen`: exit 3 = an owner setting changed since the last run (it logged ONE `config_changed` event) → repeat its lines to the owner in your first message ("Je hebt usage-guard.pause-at op 97 gezet — toegepast.") before continuing; exit 0 = nothing changed; exit 2 = a `FORGE_CONFIG.json` is damaged (the message names the file) → tell the owner in one line which file is damaged and that Forge runs with the safe defaults until it is fixed — every feature that uses their data, the network or money (usage-guard, nvidia, codex-review, mcp, portfolio, paperclip; cleanup stays report-only) is off, everything else at its default — or reset with `/forge config reset --yes` (only after the owner's yes: it keeps the damaged file as a `.damaged-<time>` backup and drops the saved settings; the gate hook treats a reset as a gate change, so it goes through the GATE HOOK yes-path), then continue the run. **Then** compose and log the applied-prefs ECHO: `node .claude/forge-bin/forge-echo.cjs emit <run_id>` — logs one `owner_prefs_loaded` event summarizing exactly which prefs/rules applied and the resolved owner config, so this ordering is visible on the dashboard, not just documented. See `.claude/skills/forge-router/SKILL.md` "Step 0-owner" for the full detail. A staged `FORGE_PREF_CANDIDATES.json` entry is never auto-active; the owner's `/forge remember <text>` (above) is the only sanctioned path that writes a new active standing rule.

## 1. Mission Intake
`run_id = forge-YYYY-MM-DD-HHMMSS` (real time). Log `run_started` (it creates the run folder), then write `.claude/forge-runs/<run_id>/run.json` (request, mode, project_type, stack, complexity, quality_target, status:"running", project_folder): draft it outside `.claude/` (e.g. `_scratch/run.json`) and put it with `node .claude/forge-bin/forge-run-file.cjs put --run <run_id> --name run.json --from _scratch/run.json` — a headless session may not Write/Edit under `.claude/` (category tests O25). Then run the config diff and emit the owner_prefs_loaded echo (see step 0) now that `run_id` exists.

**Real-fixtures intake (WAVE D, correctness-critical domains only).** If the detected project/domain is finance/invoicing, a parser, OCR, a data/ETL transform, or prediction/backtesting, check `node .claude/forge-bin/forge-fixtures.cjs check --domain <finance|parser|ocr|data|prediction> --fixtures <a,b,...>` (or `--waiver "<reason>"` when the owner has explicitly accepted the gap) BEFORE that work can honestly be called done — see `.claude/forge-fixtures/README.md` for the vault (real, owner-provided samples only, never committed). No real fixtures and no waiver = exit 3 BLOCKED (log `fixtures_required`), not a silent synthetic fallback. An explicit logged waiver unblocks it but stays visibly flagged (log `fixtures_waived`), never silent. Non-critical domains are never blocked.

## 2. Deep Prompt Analysis (load memory + ECC inventory)
Read `.claude/FORGE_PROJECT_PROFILE.md` · `FORGE_MEMORY.md` · `FORGE_TASK_HISTORY.md` · `FORGE_ECC_MODE.json` + relevant project files. Detect project type/stack. **Take the ECC inventory** (which ECC agents/skills/commands are available for this task) and log `ecc_inventory` (status `on`/`blocked` + what's available, or the reason ECC is unavailable). Log `project_scanned` · `profile_loaded` · `memory_loaded` · `agent_decision_summary`. Never fake project knowledge or ECC availability — mark `inferred`/`unknown`.

## 3. Mission Blueprint / Master Plan (the Lead Agent plans BEFORE executing)
Don't execute randomly first. As **Lead Agent**, write `.claude/forge-runs/<run_id>/mission-blueprint.md` (or `mission-packet.md`); log `mission_blueprint_created` (`expanded_mission`). The blueprint MUST include: original prompt · improved/expanded mission · **detected project type** (create a **custom taxonomy** if it's outside the usual website/n8n/RAG/scraping/fullstack/prediction set — never force-fit) · detected technologies/tools · detected project state · quality target · assumptions · constraints · **do-not-touch list** · role groups needed · selected agents · custom agents created · why each agent (and rejected agents + why) · work-package breakdown · dependencies · expected artifacts · review/rework/test strategy · definition of done · dashboard layout plan · **a Skill Discovery section (below)**.

### 3a. Skill Discovery (required before assigning subagents) — log `skill_discovery` then `skill_map_created`
The Lead Agent has **final control over skill selection**; the playbook skill lists are **examples, not limits**. Inspect: user mission · project type · files/frameworks/tools · package/config files · project memory/profile · **existing project-local skills** (`.claude/skills/`) · **global Forge skills** · **available ECC agents/skills** · available MCP/tools · quality target · required outputs · risks/dependencies. The blueprint's **## Skill Discovery** records: detected project type · detected technologies/tools · required capability areas · available skills found · skills selected · skills assigned to subagents · skills not selected + why · missing skills · custom skills needed · fallback plan. **If a needed skill doesn't exist, do not ignore the gap** — choose one: (1) create a project-local custom skill under `.claude/skills/<name>/SKILL.md` (only when safe, scoped, documented, project-local, and linked to a real subagent/work package) and log `custom_skill_created`; (2) write a custom-skill plan/scaffold for user approval; (3) assign a **native fallback method (labeled honestly)**; (4) mark the work **BLOCKED** if no safe method exists. For a genuine, evidenced capability gap worth a durable evidence-tracked proposal (not a one-off), use `node .claude/forge-bin/forge-genesis.cjs propose --gap "<x>" --evidence <file>` instead of (1) — see `.claude/skills/forge-router/SKILL.md` Step 0b for the full contract (staged-only, never live until an explicit owner `approve --owner-approval <token>`). **No executable subagent runs without an assigned skill/method/capability route.**

### 3a addendum — the `skill_map_created` format and how skills reach the agent (category tests, 2026-11-07)
Log the map with exactly this shape: `{"map":{"<agent-type>":["<skill-folder-name>", ...]}}` — the key is the agent type you dispatch (`build-boss`, `test-boss`, `ui-boss`, …) and each value is a real folder name under `.claude/skills/`, never a display name or an invented label. **Every agent type that builds, makes the UI or tests (`build-boss`, `ui-boss`, `test-boss`, `integration-boss`, `seo-boss`, the build specialists) gets the project's category playbook** — `forge-website` for a site, `forge-game` for a game, `forge-mobile` for an Android/iOS app, `forge-electron` for a desktop app, and so on — plus whatever the work needs. Example for an Android game: `{"map":{"build-boss":["forge-game","forge-mobile","forge-debug"],"ui-boss":["forge-game","forge-mobile","forge-ui-polish"],"test-boss":["forge-game","forge-testing"]}}`. Log the map BEFORE the first dispatch: Forge injects each agent's mapped skills when that agent starts, and the run contract checks that the agent really opened them (rule `skill-delivered`). A skill that was mapped but never opened turns that step red, and so does an executing agent type dispatched with no skill in any map (a later map can add skills, never remove them). The writer refuses a map that assigns no installed skill to any agent type.
For the memory update in step 12, write the memory files with `node .claude/forge-bin/forge-run-file.cjs append --file <memory file> --from <draft>` (see `forge-cmd-steps-7-14.md` step 12), never with Write/Edit under `.claude/`.
